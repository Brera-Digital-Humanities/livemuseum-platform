LiveMuseum API v1

Documentazione degli endpoint per app mobile LiveMuseum: autenticazione utenti, point of interest, foto, commenti, profili social, bookmark e itinerari.

Base URL locale: http://localhost:8091 Base URL staging: https://platform.staging.livemuseum.it Prefix: /api/v1 Auth: Authorization: Bearer <token> POI API key: X-API-KEY: <key>

Formato

Le richieste possono essere inviate come form data oppure JSON. Le risposte sono JSON.

Codice Significato
200Operazione completata.
201Utente creato.
401Credenziali o token non validi.
403Operazione non permessa, utente non attivo o registrazioni disabilitate.
422Validazione fallita. La risposta contiene errors.
429Registrazione limitata dal throttle del plugin User.

Il campo birth_date usa il formato YYYY-MM-DD. La password minima segue la configurazione di Winter.User.

Le risposte utente derivano da Winter\User\Models\User e rimuovono password, codici di reset/attivazione e persist code.

Flusso autenticazione — test rapido

# 1. LOGIN — ottieni il token
curl -s -X POST http://localhost:8091/api/v1/users/login \
  -H "Content-Type: application/json" \
  -d '{"login":"test@tester.the","password":"password123"}'
# → {"access_token":"eyJ...","user":{...}}

# Salva il token in una variabile per i comandi successivi
TOKEN="eyJ..."

# 2. VERIFICA SE LOGGATO — senza token
curl -s http://localhost:8091/api/v1/users/check
# → {"logged":false}

# Verifica con token
curl -s http://localhost:8091/api/v1/users/check \
  -H "Authorization: Bearer $TOKEN"
# → {"logged":true,"user_id":5,"username":"test@tester.the"}

# 3. CREA UN COMMENTO (serve un id da segnalare)
curl -s -X POST http://localhost:8091/api/v1/comments/1/create \
  -H "Content-Type: application/json" \
  -d '{"comment_text":"Commento di test"}'
# → {"id":9,...}

# 4. SEGNALA IL COMMENTO — richiede token
curl -s -X POST http://localhost:8091/api/v1/comments/9/report \
  -H "Authorization: Bearer $TOKEN"
# → {"comment_id":9,"reported":true,"reports_count":1,"is_hidden":false}

# 5. RIMUOVI LA SEGNALAZIONE
curl -s -X DELETE http://localhost:8091/api/v1/comments/9/report \
  -H "Authorization: Bearer $TOKEN"
# → {"comment_id":9,"reported":false,"reports_count":0,"is_hidden":false}

# 6. LOGOUT — invalida il token
curl -s -X POST http://localhost:8091/api/v1/users/logout \
  -H "Authorization: Bearer $TOKEN"
# → {"success":true}

# Dopo logout il token non è più valido
curl -s http://localhost:8091/api/v1/users/check \
  -H "Authorization: Bearer $TOKEN"
# → {"logged":false}

Point Of Interest

Rotte POI basate sui dati reali importati in quivi_poi_pois. I bookmark sostituiscono il concetto precedente di saved. Ogni POI mantiene lo stile del servizio /api/culturalSites con id_opendata, type, title, indirizzo, coordinate lat/lng, image_url, services e schedaType. schedaType e un enum: base, unlockable, livemuseum, community. Per i dati non ancora modellati, come social, immagini utente e alcuni dettagli di apertura, restano fallback provvisori. Ogni POI contiene id e slug; il dettaglio accetta entrambi.

GET /api/v1/pois/list?lat=45.4642&lng=9.1900

Restituisce POI reali vicini alle coordinate inviate, ordinati per distanza. Accetta anche bbox come alternativa a lat/lng per query viewport. Il default e 100 risultati; limit accetta valori da 1 a 500.

Parametro queryObbligoNote
latSi *Latitudine. Non richiesto se si usa bbox.
lng / lonSi *Longitudine. Non richiesto se si usa bbox.
bboxSi *Viewport: south,west,north,east (es. 41.8,12.3,42.1,12.7). Alternativo a lat/lng.
limitNoNumero risultati. Default 100, max 500.
categoryNoFiltra per categoria (es. Chiesa, Museo). Valori disponibili da /pois/categories.
schedaTypeNoFiltra per tipo scheda: base, unlockable, livemuseum, community.
typeNoFiltra per tipologia esatta (es. cappella, chiesa).
servicesNoFiltra per servizio offerto. Stringa singola o array (es. services[]=Visite+guidate). Valori: Bookshop, Visite guidate, Accesso libero, ecc.
cityNoFiltra per comune esatto (es. Milano).
provinceNoFiltra per provincia esatta (es. MI).
regionNoFiltra per regione esatta (es. Lombardia).

GET /api/v1/pois/all

Restituisce i POI reali. Richiede API key in header X-API-KEY oppure parametro api_key. La chiave lato server e configurata con POIS_API_KEY.

Supporta due modalita:

  • Paginata (consigliata): passare page e opzionalmente per_page (default 100, max 500). La risposta include un oggetto meta con total, page, per_page, last_page, has_more e paginated: true.
  • Streaming legacy: senza page, restituisce tutti i record in streaming JSON. La risposta include meta.paginated: false. Usare solo per export bulk.
Parametro queryObbligoNote
pageNoNumero di pagina (intera ≥1). Se assente, attiva la modalita streaming.
per_page / limitNoElementi per pagina. Default 100, max 500.

POST /api/v1/pois/create

Crea un nuovo POI. Campi principali: lat, lng, title, category, descr, image_url. Accetta anche source_url (URL Wikipedia / istituzionale, max 512 char) e license (es. CC BY-SA 4.0). schedaType opzionale, default base. Per compatibilita accetta lon, name, picture.

Il server calcola un dedupe_key da titolo, coordinate e citta. Se un POI con la stessa chiave esiste gia, non viene creato un duplicato.

Status rispostaHTTPSignificato
OK201POI creato. Body: {"status":"OK","id":…,"poi":{…}}
DUPLICATE200POI gia esistente. Body: {"status":"DUPLICATE","id":…,"poi":{…}}
KO422Validazione fallita. Body: {"status":"KO","errors":{…}}

Comments & Reviews

Commenti e recensioni condividono la stessa entità. Il campo kind discrimina il tipo: comment (default) o review. Le recensioni accettano un campo opzionale rating (intero 1–5). Ogni record contiene id, kind, user, comment_text, rating, comment_date, likes_num, likes, comments_num e comments per le risposte.

POST /api/v1/comments/{id}/create Auth

Crea un commento o una recensione sul target indicato da {id} (target_type: poi o picture, default poi). Per le risposte passare parent_id. Il campo rating è accettato solo se kind=review.

Campo bodyObbligoNote
comment_textSìTesto, 1–1000 caratteri.
kindNocomment (default) o review.
ratingNoIntero 1–5. Ignorato se kind non è review.
target_typeNopoi (default) o picture.
parent_idNoID del commento padre per le risposte.

GET /api/v1/comments/{id}/likes

Restituisce il conteggio like del commento e se l'utente corrente ha già messo like.

{
  "comment_id": 1,
  "likes_num": 5,
  "liked": false,
  "users": [{ "id": 2, "username": "...", "avatar": "..." }]
}

POST /api/v1/comments/{id}/like Auth

Aggiunge un like al commento per l'utente corrente. DELETE sullo stesso path rimuove il like. Risponde con liked e likes_num.

DELETE /api/v1/comments/{id}/delete Auth

Elimina solo se il commento appartiene all'utente autenticato.

PATCH /api/v1/comments/{id}/update Auth

Aggiorna comment_text; accetta anche PUT. Solo il proprietario del commento può modificarlo.

POST /api/v1/comments/{id}/report Auth

Segnala un commento. Richiede Authorization: Bearer <token>. Incrementa reports_count sul commento; se raggiunge 3 imposta automaticamente is_hidden: true. Un utente può segnalare un commento una sola volta.

curl -X POST http://localhost:8091/api/v1/comments/8/report \
  -H "Authorization: Bearer TOKEN"
// Risposta 201
{ "comment_id": 8, "reported": true, "reports_count": 1, "is_hidden": false }

// 401 se token assente o non valido
{ "error": "Token missing." }

DELETE /api/v1/comments/{id}/report Auth

Rimuove la propria segnalazione. Decrementa reports_count; se scende sotto 3 ripristina is_hidden: false.

curl -X DELETE http://localhost:8091/api/v1/comments/8/report \
  -H "Authorization: Bearer TOKEN"
// Risposta 200
{ "comment_id": 8, "reported": false, "reports_count": 0, "is_hidden": false }

Come usare il token sul frontend

Il token viene restituito da POST /api/v1/users/login nel campo access_token. Va salvato in localStorage e passato come header Authorization ad ogni chiamata autenticata.

// 1. Login e salvataggio token
const { access_token } = await fetch('/api/v1/users/login', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ login: 'email@example.com', password: '...' })
}).then(r => r.json())
// access_token === "eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9..."

localStorage.setItem('access_token', access_token)

// 2. Segnala commento
const token = localStorage.getItem('access_token')
// token === "eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9..."

await fetch(`/api/v1/comments/${commentId}/report`, {
  method: 'POST',
  headers: { 'Authorization': `Bearer ${token}` }
  // Authorization: "Bearer eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9..."
})

// 3. Verifica se loggato (non richiede auth)
const { logged } = await fetch('/api/v1/users/check', {
  headers: { 'Authorization': `Bearer ${token}` }
}).then(r => r.json())
// logged === true

Foto caricate dall'utente.

GET /api/v1/users/my/pictures Auth

Foto dell'utente autenticato.

GET /api/v1/users/my/bookmarks Auth

Bookmark dell'utente autenticato, divisi in pois, pictures, itineraries e folders.

POST /api/v1/bookmarks/create Auth

Crea un bookmark generico. Campo target_type: poi, picture o itinerary. Campo target_id obbligatorio. folder_id opzionale. DELETE /api/v1/bookmarks/delete rimuove lo stesso target.

# Bookmarkare un itinerario
TOKEN=...
curl -X POST {{baseUrl}}/api/v1/bookmarks/create \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"target_type":"itinerary","target_id":1}'

GET /api/v1/users/my/badges Auth

Badge dell'utente autenticato, inclusi quelli non ancora completati con progress e target.

POST /api/v1/users/folders/create Auth

Crea una collection. Campi: name (obbligatorio), is_public (boolean, default false). Risposta include id, name, is_public.

TOKEN=...
curl -X POST {{baseUrl}}/api/v1/users/folders/create \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"Giro Milano","is_public":true}'

PATCH /api/v1/users/folders/{id}/update Auth

Modifica name e/o is_public di una collection; accetta anche PUT. Entrambi i campi sono opzionali (almeno uno richiesto).

TOKEN=...
curl -X PATCH {{baseUrl}}/api/v1/users/folders/1/update \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"is_public":false}'

DELETE /api/v1/users/folders/{id}/delete Auth

Elimina una collection dell'utente autenticato. I bookmark contenuti vengono de-associati (folder_id = null).

GET /api/v1/users/folders/{id}

Restituisce il contenuto della collection (pois, pictures, itineraries). Se is_public = true è accessibile senza autenticazione; altrimenti richiede che il chiamante sia il proprietario (Bearer token). Risposta include is_public.

# Accesso pubblico (no token)
curl {{baseUrl}}/api/v1/users/folders/1

# Accesso privato (owner)
TOKEN=...
curl {{baseUrl}}/api/v1/users/folders/1 \
  -H "Authorization: Bearer $TOKEN"

Itinerari

Itinerari client-side: raccolte ordinate di tappe (POI). Nessuna autenticazione richiesta — il client gestisce l'ownership tramite gli ID salvati localmente.

Struttura risposta itinerario

{
  "id": 1,
  "title": "Giro del centro storico",
  "description": "Un percorso tra chiese e piazze.",
  "stops_count": 3,
  "created_at": "2026-06-11 10:00:00",
  "updated_at": "2026-06-11 10:00:00",
  "stops": [
    {
      "id": 1,
      "sort_order": 1,
      "note": "Partenza da qui",
      "poi": { "id": 42, "name": "Duomo", "type": "chiesa", ... }
    }
  ]
}

GET /api/v1/itineraries

Lista di tutti gli itinerari.

curl {{baseUrl}}/api/v1/itineraries

POST /api/v1/itineraries/create

Crea un nuovo itinerario. Campi: title (obbligatorio), description (opzionale).

curl -X POST {{baseUrl}}/api/v1/itineraries/create \
  -H "Content-Type: application/json" \
  -d '{"title":"Giro del centro","description":"Un percorso tra chiese e piazze."}'

GET /api/v1/itineraries/{id}

Dettaglio itinerario con tappe ordinate e sommario POI.

curl {{baseUrl}}/api/v1/itineraries/1

PATCH /api/v1/itineraries/{id}/update

Modifica titolo o descrizione. Accetta anche PUT.

curl -X PATCH {{baseUrl}}/api/v1/itineraries/1/update \
  -H "Content-Type: application/json" \
  -d '{"title":"Nuovo titolo"}'

DELETE /api/v1/itineraries/{id}/delete

Soft-delete dell'itinerario.

curl -X DELETE {{baseUrl}}/api/v1/itineraries/1/delete

POST /api/v1/itineraries/{id}/stops/add

Aggiunge una tappa. Campi: poi_id (obbligatorio), sort_order (default: auto-append), note (opzionale).

curl -X POST {{baseUrl}}/api/v1/itineraries/1/stops/add \
  -H "Content-Type: application/json" \
  -d '{"poi_id":42,"note":"Partenza da qui"}'

PATCH /api/v1/itineraries/{id}/stops/{stopId}/update

Modifica sort_order e/o note di una tappa.

curl -X PATCH {{baseUrl}}/api/v1/itineraries/1/stops/1/update \
  -H "Content-Type: application/json" \
  -d '{"sort_order":2,"note":"Tappa aggiornata"}'

DELETE /api/v1/itineraries/{id}/stops/{stopId}/remove

Rimuove una tappa dall'itinerario.

curl -X DELETE {{baseUrl}}/api/v1/itineraries/1/stops/1/remove

POST /api/v1/itineraries/{id}/stops/reorder

Riordina le tappe. Body: array di oggetti con id e sort_order.

curl -X POST {{baseUrl}}/api/v1/itineraries/1/stops/reorder \
  -H "Content-Type: application/json" \
  -d '{"stops":[{"id":1,"sort_order":2},{"id":2,"sort_order":1}]}'
